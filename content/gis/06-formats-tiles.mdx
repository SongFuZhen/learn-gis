## 一句话

格式决定「能不能一次搬走、能不能按需取」；瓦片决定「地图能不能秒开」。

## 1. 矢量交换格式

### GeoJSON（RFC 7946）

```json
{ "type": "FeatureCollection",
  "features": [
    { "type": "Feature",
      "properties": { "name": "西湖" },
      "geometry": { "type": "Point", "coordinates": [120.15, 30.25] } } ] }
```

- 坐标顺序 **经度在前**（lon, lat），坐标为 WGS84（4326）。
- RFC 7946 已**移除** `crs` 成员：标准 GeoJSON 只能是 4326。
- 人类可读、Web 友好；缺点是文本体积大、无索引，大文件解析慢。

<Callout type="example" title="例子 · 坐标写反会怎样">
以西湖为例，正确写法是 `"coordinates": [120.15, 30.25]`（经度在前）。如果不小心写成 `[30.25, 120.15]`，纬度就变成了 120.15。纬度的合法范围是 -90 到 90，多数库会直接报错；即使静默接受，点也会落到完全错误的位置。这是 Web 地图开发里最高频的低级错误。
</Callout>

### Shapefile

至少三件套：`.shp`（几何）、`.shx`（索引）、`.dbf`（属性），常带 `.prj`（CRS）。

老而普遍，但限制明显：

- 单文件 **2 GB** 上限
- 字段名最长 **10 字符**
- 一个图层只能一种几何类型
- 无拓扑
- 编码不统一，中文属性容易乱码

<Callout type="example" title="例子 · 10 字符字段名">
假如属性表里有个字段叫「土地利用类型」，写进 Shapefile 后字段名最多只剩 10 个字符，设计者只能改成 `TDLYLX` 之类的拼音缩写。很多老 GIS 数据里字段名像「谜语」，因为 Shapefile 只给了 10 个字符。
</Callout>

### GeoPackage（.gpkg）

一个 **SQLite 文件**装下矢量、栅格与瓦片，OGC 标准，支持空间索引。现代桌面/移动端交换的首选之一。

### 其他

- **KML**：Google Earth 生态，带样式。
- **GPX**：GPS 轨迹/航点。
- **TopoJSON**：把共享边界存成 `arcs`，体积可显著小于 GeoJSON，保留拓扑。

<Callout type="must" title="必背 · 矢量格式">
- GeoJSON：**经度在前**（lon, lat），坐标固定 **WGS84（4326）**
- RFC 7946 已**移除** `crs` 成员，标准 GeoJSON 只能是 4326
- Shapefile 三件套：`.shp`（几何）、`.shx`（索引）、`.dbf`（属性），`.prj` 存 CRS
- Shapefile 硬限制：**2 GB** 上限、字段名 **10 字符**
- GeoPackage = **一个 SQLite 文件**装下矢量、栅格与瓦片
</Callout>

## 2. 栅格格式

- **GeoTIFF**：TIFF + 地理参考（CRS、仿射变换），GIS 栅格的事实标准。
- **COG（Cloud Optimized GeoTIFF）**：分块 + 内置概览（overviews）+ 元数据在文件头部，客户端可用 HTTP Range 只取需要的块，无需下载整个文件。

<Callout type="example" title="例子 · COG 只取需要的那一块">
一幅 **10 GB** 的卫星影像做成 COG 挂在 HTTP 服务器上。前端只想预览某个约 **256 KB** 的小区域：传统 GeoTIFF 要把 10 GB 全下完才能打开；COG 因为元数据在文件头部，客户端先读头部、算出目标块的位置，再发一个 HTTP Range 请求只取那 256 KB，流量从 GB 级降到 KB 级。类比：去图书馆只复印需要的那一页，而不是把整本书借走。
</Callout>

<Callout type="must" title="必背 · 栅格格式">
- GeoTIFF = TIFF + 地理参考（CRS、仿射变换），GIS 栅格**事实标准**
- COG 三要素：**分块**、内置**概览**（overviews）、**元数据在文件头部**
- COG 靠 **HTTP Range** 按需取块，不必下载整个文件
</Callout>

## 3. 瓦片：把地图切片

瓦片金字塔：`z` 缩放级、`x` 列、`y` 行，每级 2^z × 2^z 张图。

```
z=0: 1 张
z=1: 4 张
z=10: 1,048,576 张
```

两种编号约定：

- **XYZ（Google/OSM）**：`y` 从顶部（北）开始。
- **TMS**：`y` 从底部（南）开始，换算 `y_tms = 2^z - 1 - y_xyz`。

反了会上下颠倒，是瓦片接入最常见的坑。

<Callout type="example" title="例子 · 算一算瓦片数量和 TMS 行号">
**瓦片数**：z=10 时，每级瓦片数 = 2^10 × 2^10 = 1024 × 1024 = **1,048,576** 张——每升一级数量翻 4 倍，这就是叫「金字塔」的原因。

**TMS 换算**：某瓦片 XYZ 编号为 z=10, x=840, y=388，转成 TMS 行号：

1. 先算该级总行数：2^10 = 1024；
2. 套公式：y_tms = 2^10 − 1 − 388 = 1023 − 388 = **635**；
3. `z=10, x=840, y=388`（XYZ）和 `z=10, x=840, y=635`（TMS）是**同一张图**，只是 y 一个从北往南数、一个从南往北数。
</Callout>

<Callout type="must" title="必背 · 瓦片编号">
- 瓦片地址 = **z**（缩放级）、**x**（列）、**y**（行），每级 **2^z × 2^z** 张
- z=0 全世界 **1 张**，z=1 有 **4 张**
- **XYZ**：y 从**北**（顶部）数；**TMS**：y 从**南**（底部）数
- 换算公式：**y_tms = 2^z − 1 − y_xyz**；用反了地图**上下颠倒**
</Callout>

## 4. 矢量瓦片（MVT）

矢量瓦片是 **protobuf 编码的几何 + 属性**（Mapbox Vector Tile 规范），不是图片：

1. 服务端切片、按 z 级简化；
2. 客户端拿到数据后用样式（style JSON）渲染；
3. 一份瓦片可以换多套样式、支持交互查询，体积通常远小于同范围 GeoJSON。

**PMTiles** 把整层瓦片打包成单个文件，通过 Range 请求按需读取，可直接放在对象存储上，省掉瓦片服务。

<Callout type="example" title="例子 · 一份瓦片，N 套皮肤">
同一家公司的全国底图只需要**切一次**矢量瓦片：白天的亮色样式、夜间的暗色样式，只是两份不同的 style JSON，客户端拿到同一份 MVT 数据，按各自样式渲染。若用栅格瓦片，这两种外观就得切两次图、存两份瓦片。这就是「渲染放到客户端」最直接的收益。
</Callout>

<Callout type="must" title="必背 · 矢量瓦片">
- MVT = **protobuf 编码的「几何 + 属性」**，不是图片
- 服务端切片简化，**渲染在客户端**（style JSON）
- 一份瓦片可换**多套样式**、支持交互查询
- PMTiles：整层打包成**单文件**，Range 请求按需读，可直接放**对象存储**
</Callout>

## 5. 怎么选

| 场景 | 建议 |
|---|---|
| 前后端交换、小数据 | GeoJSON |
| 桌面 GIS 互操作 | Shapefile / GeoPackage |
| 全国/全球底图、热点图 | 矢量瓦片（MVT）+ 客户端渲染 |
| 影像/高程发布 | COG / GeoTIFF + 瓦片服务 |
| 静态托管、无服务端 | PMTiles |
