> 老司机 3 分钟经验之谈。看懂这块，本章就懂了 80%；下面是可以慢慢查的完整版。

**这章解决什么问题**：空间分析在代码和数据库里怎么落地——前端用 Turf.js，后端用 PostGIS。空间运算本身不难，难的是**单位、SRID、索引**三件事，搞错任何一件，结果都静默地错。

**我的经验一句话**：把空间函数当普通 API 用，但**永远先问单位**。两个最出名的坑我都见过：

- `turf.buffer(point, 1000)` 想画 1000 米的服务圈——Turf 默认单位是**公里**，实际画了个 1000 公里的巨无霸，覆盖了半个中国。
- PostGIS 里 `geometry` 类型在 4326 下 `ST_Distance` 返回的是「度」——不是米，没有业务意义。要米，用 `geography` 类型或先转投影。

**我见过的坑（你大概率也会踩）**：

- **忘了建空间索引**：百万条数据的相交查询跑几分钟；建个 GiST 索引（`CREATE INDEX ... USING GIST(geom)`）变毫秒。
- **SRID 不一致直接 join**：两张表一个 4326 一个 3857，查询结果全错还不报错。先 `ST_Transform` 统一。
- **前端扛大数据**：十万条要素全推给浏览器直接卡死——重计算下沉到 PostGIS，前端只拿结果。

**必记 3 条**：

1. Turf 默认单位是公里，不是米
2. PostGIS 里 geography 按米算球面距离，geometry 看 SRID 单位
3. 空间表必须建 GiST 索引；SRID 不一致先转换

## 一句话

空间运算本身不难，难的是「单位、SRID（/ˌɛs ˌɑːr ˌaɪ ˈdiː/，「艾斯-阿-艾-迪」）、索引」三件事；搞错任何一件，结果就会静默地错误。

## 1. 前端：Turf.js

```js
import { buffer } from "@turf/turf";
const buf = buffer(point, 5, { units: "kilometers" });
```

- `turf.distance(a, b)` 默认单位 **kilometers**。
- `turf.area(polygon)` 返回 **平方米**（球面计算）。
- `turf.buffer` 的半径单位由 `options.units` 指定，**默认 kilometers**。
- Turf（/tɜːrf/，「特尔夫」）在经纬度上做球面近似，适合交互与轻量分析；大数据、精确椭球计算交给后端。

<Callout type="must" title="必背 · Turf 的单位">
- `turf.distance` 默认单位是**公里**，不是米
- `turf.area` 返回**平方米**（球面近似）
- `turf.buffer` 半径单位由 `options.units` 决定，**默认公里**
- Turf 是球面近似，适合交互；精确椭球计算交给后端
</Callout>

<Callout type="example" title="例子 · 单位陷阱是怎么发生的">
想给一个门店画 1 公里的服务范围：

```js
const buf = buffer(point, 1, { units: "kilometers" }); // ✅ 1 公里
const oops = buffer(point, 1000);                       // ❌ 1000 公里！
```

漏掉 `units` 时半径默认按**公里**算，写 `1000` 想表达「1000 米」，实际画出一个 1000 公里的巨型缓冲区。地图上放大看局部根本察觉不到，等业务方发现「覆盖了半个中国」就晚了。
</Callout>

## 2. 后端：PostGIS 的两种几何

| 类型 | 计算平面 | 单位 | 适用 |
|---|---|---|---|
| `geometry` | 平面（按 SRID 的坐标单位） | 度 / 米 | 投影后数据、制图、叠加分析 |
| `geography` | 椭球面 | 米 | 全球距离、跨带数据 |

```sql
-- 4326 的 geometry：单位是「度」
SELECT ST_Distance(a.geom, b.geom) FROM ...;   -- 得到度数

-- geography：单位是「米」
SELECT ST_Distance(a.geog, b.geog) FROM ...;   -- 得到米
```

<Callout type="example" title="例子 · 同一段距离，两种答案">
北京 (116.4, 39.9) 与上海 (121.5, 31.2) 之间量距离：

1. **geometry（SRID 4326）**：把经纬度当平面坐标算直线距离：
   `sqrt((121.5-116.4)² + (31.2-39.9)²) = sqrt(5.1² + 8.7²) ≈ 10.1`
   返回 **10.1**，单位是「度」，既不是公里也不是米，没有业务意义。
2. **geography**：沿椭球面量测，返回约 `1068000`，单位是**米**，约 1068 公里，和地图软件量的基本一致。

同一个函数 `ST_Distance`，类型不同，答案差 10 万倍，而且**不报任何错**。
</Callout>

## 3. 必记函数

```sql
ST_Transform(geom, 3857)      -- 投影转换（改 SRID 并换算坐标）
ST_SetSRID(geom, 4326)        -- 只贴标签，不换算（危险）
ST_DWithin(a, b, 1000)        -- 距离 <= 1000（可用索引）
ST_Intersects(a, b)           -- 是否相交（可用索引）
ST_Contains(a, b)             -- a 包含 b
ST_Within(a, b)               -- a 在 b 内（与 Contains 方向相反）
ST_Buffer(geom, 500)          -- 缓冲区，单位 = CRS 单位
ST_Area / ST_Length           -- 面积/长度，单位 = CRS 单位
ST_AsGeoJSON(geom)            -- 转 GeoJSON
ST_MakeEnvelope(x1,y1,x2,y2, srid)  -- 构造矩形，做范围查询
```

<Callout type="must" title="必背 · 函数易混点">
- `ST_Transform` 会**换算坐标**；`ST_SetSRID` 只**贴标签不换算**，不改变任何坐标值
- `ST_Contains(a, b)` 是「a 包含 b」，`ST_Within(a, b)` 是「a 在 b 内」，**方向相反**，参数别写反
- 判断「距离不超过 r」用 `ST_DWithin(a, b, r)`，不要用 `ST_Distance` 再比较，前者能用索引
- `ST_Buffer` / `ST_Area` / `ST_Length` 的单位 = **当前 CRS（/ˌsiː ˌɑːr ˈɛs/，「西-阿-艾斯」）的单位**，4326 上就是「度」
</Callout>


## 4. 叠加函数族：合并、求交、求差

第 10 章讲叠置分析的「语义」（交/并/差解决什么问题），这里补上 PostGIS（/ˌpoʊstˈdʒɪs/，「剖斯特-吉斯」）的「语法」：

```sql
-- 合并：注意 ST_Union 与 ST_Collect 的区别
ST_Union(geom)      -- 真合并：融掉公共边界，重叠部分只算一次
ST_Collect(geom)    -- 只打包：快，但保留内部边界与重叠

-- 求交 / 求差
ST_Intersection(a, b)   -- 交集：两图层都覆盖的部分
ST_Difference(a, b)     -- 差集：a 减去与 b 重叠的部分
```

空间连接（把位置当外键）的完整 SQL 长这样：

```sql
-- 把每个 POI 挂上它所在区的名字：不用 POI 表存区名
SELECT p.id, d.name AS district
FROM poi p
JOIN districts d ON ST_Within(p.geom, d.geom);
```

**大几何与大表**：一个几万个顶点的行政边界，每次相交判断都很贵。`ST_Subdivide(geom)` 把大几何切成小碎块，配合 GiST（/dʒɪst/，「吉斯特」）的 `&&` 粗筛，能让大表叠加快一个数量级：

```sql
CREATE TABLE districts_sub AS
SELECT ST_Subdivide(geom, 256) AS geom, name FROM districts;
```

**有效性检查**（第 05 章的概念，这里是工程落地）：

```sql
SELECT id, ST_IsValidReason(geom)
FROM parcels
WHERE NOT ST_IsValid(geom);        -- 找出所有脏几何

UPDATE parcels
SET geom = ST_MakeValid(geom)      -- 就地修复
WHERE NOT ST_IsValid(geom);
```

<Callout type="must" title="必背 · 叠加函数四句">
- **ST_Union** 真合并（融边界、去重叠）；**ST_Collect** 只打包（快，边界还在）。聚合统计用 Union，简单分组用 Collect
- **ST_Intersection** 求交、**ST_Difference** 求差，选址 = 交，剔除 = 差
- 大表叠加前先 `ST_Subdivide` 切碎大几何，配合索引快一个数量级
- 入库先跑 `ST_IsValid`，脏数据用 `ST_MakeValid` 修复
</Callout>

<Exercise
  tool="sql"
  title="练习：空间连接——POI 挂区名"
>
  表：`poi(id, geom)`（点）、`districts(id, name, geom)`（面），都是 EPSG:4326。
  写 SQL：给每个 POI（/ˌpiː ˌoʊ ˈaɪ/，「皮-欧-艾」）挂上所在区的 `name`；没有落在任何区里的 POI 也要保留（提示：LEFT JOIN）。

  <ExerciseSolution>
    ```sql
    SELECT p.id, d.name
    FROM poi p
    LEFT JOIN districts d ON ST_Within(p.geom, d.geom);
    ```

    要点：ST_Within 的参数方向（点在内、面在外）；LEFT JOIN 保留区外的点，
    其 name 为 NULL，这行数据本身就是「边界外数据」的质量线索。
  </ExerciseSolution>
</Exercise>

<Exercise
  tool="sql"
  title="练习：缓冲 + 求交——选址小工作流"
>
  需求：找「地铁站 500 m 服务范围 ∩ 商业用地」的候选地块（米制 CRS 32650）。

  <ExerciseSolution>
    ```sql
    SELECT d.gid
    FROM landuse d
    WHERE d.type = 'commercial'
      AND ST_Intersects(d.geom, ST_Buffer(metro.geom, 500));
    ```

    更完整的写法：先把多站缓冲区 ST_Union 融合成一片，再与商业用地求交：

    ```sql
    WITH buf AS (
      SELECT ST_Union(ST_Buffer(geom, 500)) AS geom FROM metro
    )
    SELECT d.gid
    FROM landuse d, buf
    WHERE d.type = 'commercial'
      AND ST_Intersects(ST_Intersection(d.geom, buf.geom), buf.geom);
    ```

    记住三件事：32650 是米制，500 就是 500 米；多站缓冲先 ST_Union 融合；
    求交后用 ST_Intersects 过滤空几何。
  </ExerciseSolution>
</Exercise>

## 5. 索引：让查询真的快


```sql
CREATE INDEX ON roads USING GIST (geom);

-- ✅ 能用索引
WHERE geom && ST_MakeEnvelope(116.2,39.8,116.6,40.1,4326)
  AND ST_Intersects(geom, ...)
WHERE ST_DWithin(geom, :p, 1000)

-- ❌ 用不上索引（全表算距离）
WHERE ST_Distance(geom, :p) < 1000
```

GiST 索引靠外接矩形（`&&`）先粗筛。`ST_DWithin` 内部会先做 bbox 判断，所以比 `ST_Distance < x` 快得多。

最近邻：

```sql
SELECT * FROM poi ORDER BY geom <-> ST_Point(116.4, 39.9, 4326) LIMIT 5;
```

<Callout type="must" title="必背 · 索引规则">
- GiST 靠**外接矩形（`&&`）**先粗筛，再做精确判断
- 能走索引：`&&` + `ST_Intersects`、`ST_DWithin`、`ORDER BY geom <-> 点`
- 走不了索引：`ST_Distance(geom, p) < r`，全表逐行算距离
- 最近邻固定写法：`ORDER BY geom <-> 点 LIMIT n`
</Callout>

<Callout type="example" title="例子 · 打车软件找最近的车">
乘客在 (116.4, 39.9)，要找最近的 5 辆车，表里有 500 万条车辆位置：

```sql
SELECT id FROM cars
ORDER BY geom <-> ST_Point(116.4, 39.9, 4326)
LIMIT 5;
```

`<->` 是 KNN（/ˌkeɪ ˌɛn ˈɛn/，「凯-恩-恩」）运算符，直接在 GiST 索引上按距离排序，毫秒级出结果。等价的「笨写法」是先给 500 万行每行算一遍 `ST_Distance`，再排序取前 5 条，结果一样，慢几百倍。
</Callout>

## 6. 三个静默错误

1. **在 4326 上做 buffer**：`ST_Buffer(geom, 1000)` 得到的是「1000 度」的怪物。先 `ST_Transform` 到米制 CRS，或用 `geography`。
2. **只改 SRID 不转换**：`ST_SetSRID` 只是换标签，位置不变。
3. **在 3857 上量面积**：高纬度面积被严重高估；用等积投影或 `geography`。

<Callout type="must" title="必背 · 三个静默错误">
- 4326 上 `ST_Buffer(geom, 1000)` 得到的是「**1000 度**」的怪物，先 `ST_Transform` 到米制 CRS，或用 `geography`
- `ST_SetSRID` **不换算坐标**，只改 SRID 标签
- 3857 **不能量面积**，高纬度严重高估，用等积投影或 `geography`
- 这三类错都**不报错**，只返回错误结果，必须形成肌肉记忆
</Callout>

<Callout type="example" title="例子 · 3857 上量面积会差多少">
在北京（约 40°N）量一块真实面积 100 平方公里的地块：

1. Web Mercator（/wɛb mərˈkeɪtər/，「韦布-默-凯-特」）的线性放大倍数 = `1 / cos(40°) ≈ 1.31`
2. 面积放大倍数 = 线性倍数的平方 ≈ `1.31 × 1.31 ≈ 1.70`
3. `ST_Area` 在 3857 上返回约 **170 平方公里**，凭空多出 70%，且不报错。

换成等积投影，或用 `geography` 类型的 `ST_Area`，才会得到接近 100 平方公里的正确值。
</Callout>

## 7. 组合建议

- 展示/交互：Turf 在前端，数据量小、延迟低。
- 需要索引、事务、大数据、精确统计：PostGIS。
- 前端只传参数，后端返回 GeoJSON（/ˈdʒiːoʊˌdʒeɪsən/，「吉欧-杰森」）：`ST_AsGeoJSON(ST_Transform(...))`。
